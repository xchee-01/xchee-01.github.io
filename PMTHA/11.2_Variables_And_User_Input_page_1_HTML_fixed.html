MODULE 1: Variables and Command Substitution

Welcome to the exciting world of interactive Linux shell scripting! In this module, you'll master shell variables and command substitution - essential tools for creating dynamic scripts that adapt to different situations.

Fun Fact: The $ symbol in shell variables comes from early computing when memory was so precious that single-character symbols were preferred. It's been with us since the 1970s!

What Are Variables?

Variables are labeled containers that store information your scripts can use. System administrators use them to store server names, file paths, and configuration settings.

Creating Variables:

# No spaces around the equals sign! server_name="web-server-01" deployment_date="2024-01-15" max_connections=100
Copied!
Learning Checkpoint
Which of the following is the correct way to assign a variable in shell scripting?
name = value
With spaces around the equals sign
Not quite! Spaces around the equals sign will cause an error. Shell interprets this as a command 'name' with arguments '=' and 'value'.
name=value
No spaces around the equals sign
Correct! In shell scripting, variable assignment must have no spaces around the equals sign. This is a fundamental rule!
$name=value
With dollar sign before the name
Incorrect! The $ symbol is used to access variable values, not to assign them. Use $ only when referencing the variable.
set name=value
Using the set command
That's not right. The 'set' command has different purposes in shell scripting. Direct assignment without any command is the correct approach.

Using Variables:

echo "Connecting to $server_name" echo "Deployment scheduled for: $deployment_date" echo "Maximum connections: $max_connections"
Copied!
Learning Checkpoint
If server_name="web-server-01", what will echo "Connecting to $server_name" display?
Connecting to web-server-01
The variable is expanded to its value
Correct! The shell replaces $server_name with its value "web-server-01" before displaying the text.
Connecting to $server_name
The text is displayed literally
Not quite! When using double quotes, the shell expands variables. Use single quotes if you want literal text.
Connecting to
The variable part is omitted
Incorrect! The shell doesn't omit variables; it replaces them with their values.
Error: undefined variable
An error occurs
That's not right. Since the variable was defined, it will be expanded to its value without error.

Command Substitution

Capture command output using $(...) syntax:

current_date=$(date +%Y-%m-%d) current_user=$(whoami) system_load=$(uptime | awk '{print $10}') echo "Backup date: $current_date" echo "Running as: $current_user"
Copied!
Learning Checkpoint
What does current_date=$(date +%Y-%m-%d) do?
Executes date command and stores output
Runs the date command and assigns its output to current_date
Correct! The $(...) syntax executes the command inside and captures its output into the variable.
Stores the text "date +%Y-%m-%d"
Assigns the literal command text to the variable
Not quite! The $(...) syntax executes the command, it doesn't store it as text.
Creates an alias for the date command
Makes current_date an alias
Incorrect! This creates a variable with the command's output, not an alias.
Schedules the date command to run
Sets up a scheduled task
That's not right. Command substitution executes immediately and captures the output.

Variable Naming Best Practices

# Good names (descriptive and lowercase) backup_directory="/mnt/backup" log_file_path="/var/log/myapp.log" # Avoid these patterns x="data" # Too vague! BACKUPDIR="/backup" # Reserved for environment backup-dir="/backup" # Hyphens not allowed
Copied!
Learning Checkpoint
Which variable name follows shell scripting best practices?
backup_directory
Lowercase with underscores, descriptive
Correct! This follows best practices: lowercase, descriptive, and uses underscores for word separation.
BACKUPDIR
All uppercase
Not ideal! Uppercase names are conventionally reserved for environment variables and constants.
backup-dir
With hyphens
Incorrect! Hyphens are not allowed in variable names. Use underscores instead.
x
Single letter
Poor choice! Single-letter variables are not descriptive and make code hard to understand.

Advanced Variable Techniques

Default Values:

# Use default if variable is unset/empty config_file=${CONFIG_FILE:-"/etc/myapp/config.conf"} log_level=${LOG_LEVEL:-"INFO"}
Copied!
Learning Checkpoint
If CONFIG_FILE is not set, what value will config_file have after: config_file=${CONFIG_FILE:-"/etc/myapp/config.conf"}
/etc/myapp/config.conf
The default value after :-
Correct! The :- operator provides a default value when the variable is unset or empty.
Empty string
Nothing is assigned
Not right! The :- operator ensures a default value is used when the variable is unset.
CONFIG_FILE
The variable name itself
Incorrect! The syntax checks if CONFIG_FILE is set and uses the default if not.
Error occurs
Script fails
That's not right. This syntax is designed to handle unset variables gracefully.

String Operations:

# Length username="administrator" echo "Length: ${#username}" # Substring extraction email="admin@company.com" echo "Username: ${email%@*}" echo "Domain: ${email#*@}" # Path manipulation file_path="/var/log/system.log" echo "Directory: ${file_path%/*}" echo "Filename: ${file_path##*/}"
Copied!
Learning Checkpoint
If email="admin@company.com", what does ${email%@*} return?
admin
Everything before the @ symbol
Correct! The %@* pattern removes everything from @ to the end, leaving the username part.
company.com
Everything after the @ symbol
Not quite! That would be ${email#*@}. The % removes from the end, not the beginning.
admin@company.com
The entire email unchanged
Incorrect! The % operator removes the matching pattern from the end of the string.
@
Just the @ symbol
That's not right. The pattern removes the @ and everything after it.
Learning Checkpoint
Given file_path="/var/log/system.log", what does ${file_path##*/} return?
system.log
Just the filename
Correct! The ##*/ pattern removes everything up to and including the last slash, leaving just the filename.
/var/log
The directory path
Not quite! That would be ${file_path%/*}. The ## removes from the beginning.
log/system.log
Last two path components
Incorrect! The ## operator performs greedy matching and removes everything up to the last /.
/var/log/system.log
The entire path unchanged
That's not right. The ##*/ pattern removes the directory path portion.

Case Conversion:

environment="production" echo "${environment^^}" # PRODUCTION echo "${environment^}" # Production
Copied!
Learning Checkpoint
What's the difference between ${var^^} and ${var^}?
^^ converts all to uppercase, ^ only first letter
Double caret for all characters, single for first
Correct! ^^ converts the entire string to uppercase, while ^ only capitalizes the first letter.
Both convert to uppercase
No difference between them
Not quite! There's an important difference in how many characters they convert.
^^ is uppercase, ^ is lowercase
They convert in opposite directions
Incorrect! Both convert to uppercase; use ,, for lowercase conversion.
^ is faster than ^^
Performance difference only
That's not the difference. They affect different numbers of characters.

Environment Variables

Access system-wide configurations:

echo "Current user: $USER" echo "Home directory: $HOME" echo "System PATH: $PATH" echo "Process ID: $$"
Copied!
Learning Checkpoint
What does the special variable $$ represent?
Current process ID
The PID of the running shell script
Correct! $$ gives you the process ID of the current shell or script, useful for creating unique temporary files.
Last command's exit status
The return code of the previous command
Not quite! That would be $?. $$ is for the process ID.
Number of arguments
Count of script parameters
Incorrect! That would be $#. $$ gives the process ID.
Script name
The name of the current script
That's not right. Script name is $0. $$ is the process ID.

Export variables for child processes:

export DATABASE_URL="postgres://localhost:5432/mydb" export LOG_LEVEL="DEBUG"

#!/bin/bash # Configuration with defaults db_host=${DB_HOST:-"localhost"} db_port=${DB_PORT:-"5432"} db_name=${DB_NAME:-"app_db"} # Validate port if ! Learning Checkpoint
What does the regex ^[0-9]+$ match in the port validation?
Only numeric strings
Strings containing only digits from start to end
Correct! ^ anchors to start, [0-9]+ matches one or more digits, $ anchors to end. This ensures the entire string is numeric.
Any string with numbers
Strings that contain at least one digit
Not quite! The ^ and $ anchors mean the ENTIRE string must be digits only.
Numbers at the start
Strings beginning with digits
Incorrect! The $ at the end requires the string to end with digits too, meaning all digits.
Single digit only
Exactly one numeric character
That's not right. The + means one or more digits, not just one.

Quick Reference

# Assignment var="value" var=$(command) # Access echo $var echo ${var} echo "${var}" # Defaults ${var:-default} ${var:=default} # String operations ${#var} # Length ${var:2:5} # Substring ${var#pattern} # Remove from start ${var%pattern} # Remove from end ${var/old/new} # Replace first ${var//old/new} # Replace all ${var^^} # Uppercase ${var,,} # Lowercase

Final Knowledge Check
What's the difference between ${var:-default} and ${var:=default}?
:- uses default, := assigns default
:- only substitutes, := also sets the variable
Excellent! :- provides a default value for that use only, while := assigns the default to the variable for future use too.
No difference
They work the same way
Not quite! There's an important difference in whether they modify the variable.
:- is for strings, := for numbers
They handle different data types
Incorrect! Both work with any value type. The difference is in assignment behavior.
:= is faster
Performance optimization
That's not the difference. They have different behaviors regarding variable assignment.
