1.2.3. Comments - Your Laboratory Notebook in Code

🎯 Learning Objectives

  • Write clear, helpful comments like a research scientist
  • Learn commenting best practices for medical code
  • Understand when and how to document your code

🧠 Cognitive Load Management

Start with single-line comments, then build up to documentation strategies used in real medical software.

In laboratory research, meticulous documentation is essential. Comments in Python serve the same purpose as a lab notebook - they explain what your code does, why certain decisions were made, and provide context for future researchers (including yourself!).

🔬 Lab Notebook Wisdom: "The palest ink is better than the best memory" - Chinese Proverb. In coding, we say: "Code tells you HOW, comments tell you WHY."

💬 The Anatomy of a Python Comment

Comments start with # and Python completely ignores everything after it on that line:

# This is a comment - Python ignores this completely! print("This code runs normally") # This is also a comment # You can have multiple comment lines # to explain complex medical procedures # like this multi-step diagnostic protocol
Copied!
Learning Checkpoint
Which of the following is the correct way to write a comment in Python?
// This is a comment
C++ or JavaScript style comment
Not quite. This is the comment syntax for C++ or JavaScript, not Python.
/* This is a comment */
C-style multi-line comment
Incorrect. This is C-style comment syntax, not used in Python.
# This is a comment
Python comment with hash symbol
Correct! In Python, comments always start with the # symbol. Everything after # on that line is ignored by Python.
-- This is a comment
SQL-style comment
No, this is SQL comment syntax. Python uses # for comments.

🏥 Medical Commenting Best Practices

1. Document Critical Values

# Maximum safe dose: 1000mg per day (FDA guidelines) max_dose = 1000 # Normal blood glucose range: 70-100 mg/dL (fasting) glucose_normal_min = 70 glucose_normal_max = 100
Copied!

2. Explain Medical Decisions

# Using 98.6°F as baseline (traditional value) # Note: Modern research suggests 97.5-98.9°F range normal_temp = 98.6
Copied!

3. Add Important Warnings

# WARNING: This algorithm is for research only # NOT approved for clinical diagnosis # Requires FDA approval before patient use
Copied!
Learning Checkpoint
In medical coding, which type of comment is MOST important to include?
Comments explaining basic Python syntax
Like # This adds two numbers
While helpful for beginners, syntax explanations are less critical than medical information.
Comments documenting critical medical values and their sources
Like # Max dose: 1000mg (FDA guidelines)
Correct! When coding for medical applications, documenting critical values (like dosages, normal ranges) and their sources (FDA guidelines, research papers) is essential for safety and verification.
Comments describing what each line of code does
Like # Increment counter by 1
Over-commenting obvious code can clutter the program. Focus on the WHY, not the WHAT.
Comments with programmer's personal notes
Like # I think this works...
Personal notes are unprofessional and don't help with medical safety or compliance.

📋 Comment Patterns for Medical Code

TODO Comments - Things to add later:

# TODO: Add pediatric dosing calculations # TODO: Integrate with hospital EMR system adult_dose = 500
Copied!

FIXME Comments - Known issues:

# FIXME: Currently doesn't handle patients under 18 # FIXME: Need to add allergy checking
Copied!

NOTE Comments - Important information:

# NOTE: This uses the 2023 WHO diagnostic criteria # NOTE: Validated on 10,000 patient dataset
Copied!
Learning Checkpoint
You've discovered a bug in your medical dosage calculator that doesn't account for kidney function. Which comment pattern should you use?
TODO: Account for kidney function in dosage
Mark it as a future enhancement
TODO is for new features, not fixing existing bugs. This is a critical issue that needs fixing.
FIXME: Dosage calculation doesn't consider kidney function
Mark it as a bug to fix
Correct! FIXME is used for known issues or bugs that need to be corrected. Since this is a discovered bug that could affect patient safety, FIXME is the appropriate pattern.
NOTE: Kidney function affects dosage
Document the medical fact
NOTE is for important information, not bugs. This doesn't convey the urgency of fixing the issue.
# Kidney function bug
Just a simple comment
Too vague. Using standard patterns like FIXME helps other developers quickly identify and prioritize issues.

🤖 Self-Documenting Code vs Comments

Sometimes good variable names reduce the need for comments:

# Bad: Needs a comment x = 120 # Systolic blood pressure # Good: Self-documenting systolic_blood_pressure = 120

1.2.4. Case Sensitivity - Precision in Medical Coding

🎯 Learning Objectives

  • Master Python's case sensitivity rules
  • Avoid common capitalization errors
  • Understand how case sensitivity prevents medical mistakes

🧠 Cognitive Load Management

We'll use memorable medical examples where case matters critically, making the concept unforgettable.

In medicine, precision matters. The difference between "mg" and "Mg" could be life-threatening (milligrams vs magnesium). Python is similarly case-sensitive - every capital letter matters!

⚠️ Critical Concept: In Python, glucose, Glucose, and GLUCOSE are three completely different variables - like three different patients with similar names!

🔤 The Case Sensitivity Rules

Everything in Python is case-sensitive:

  • Variable names
  • Function names
  • Keywords
  • Everything except comments!

💊 Medical Case Examples

# These are THREE different variables! medication = "Aspirin" # lowercase - regular variable Medication = "Tylenol" # Capitalized - different variable! MEDICATION = "Ibuprofen" # ALL CAPS - yet another variable! print(medication) # Prints: Aspirin print(Medication) # Prints: Tylenol print(MEDICATION) # Prints: Ibuprofen
Copied!
Learning Checkpoint
In Python, which of these statements is TRUE?
glucose and Glucose refer to the same variable
Python treats them as identical
Incorrect. Python is case-sensitive, so glucose and Glucose are different variables.
GLUCOSE and glucose are different variables
They can hold different values
Correct! Python is case-sensitive for everything. glucose, Glucose, and GLUCOSE are three completely different variables that can hold different values.
Python converts all variables to lowercase automatically
For consistency
No, Python preserves the exact case you use. It never automatically converts variable names.
Case only matters for function names, not variables
Variables are case-insensitive
Wrong. Case sensitivity applies to ALL identifiers in Python - variables, functions, classes, everything.

🧬 Gene Naming Conventions

In bioinformatics, case often has meaning:

# Common convention in genetics brca1 = "gene" # Gene name (lowercase italic in papers) BRCA1 = "protein" # Protein name (uppercase) Brca1 = "mouse gene" # Mouse gene (first letter capitalized) print(f"Human gene: {brca1}") print(f"Human protein: {BRCA1}") print(f"Mouse homolog: {Brca1}")
Copied!
Learning Checkpoint
Following standard bioinformatics conventions, which variable would store a human protein?
p53 = "tumor suppressor"
Lowercase format
This follows gene naming convention (lowercase). Proteins use uppercase.
P53 = "tumor suppressor"
Uppercase format
Correct! In bioinformatics conventions, human proteins are written in all uppercase (P53), while genes are lowercase (p53). This helps distinguish between genes and their protein products.
P53 = "tumor suppressor"
Mixed case format
This actually shows the same as option B (P53). Both B and C would be correct for a human protein.
p53 = "tumor suppressor"
Another lowercase format
Same as option A - this is gene notation, not protein notation.

⚡ Common Case Errors

Error 1: Wrong case for print

# This will cause a NameError! Print("Hello") # Wrong! 'Print' is not defined print("Hello") # Correct! 'print' is lowercase
Copied!

Error 2: Inconsistent variable names

bloodPressure = 120 print(bloodpressure) # NameError! Python doesn't know bloodpressure
Copied!
Learning Checkpoint
This code produces an error. What's the problem?
patient_Temperature = 98.6 if patient_temperature > 100: print("Fever detected")
The if statement syntax is wrong
Missing colon or indentation
The if statement syntax is correct. The issue is elsewhere.
Temperature values should be integers, not decimals
98.6 should be 98
Python handles decimal numbers (floats) perfectly fine for temperatures.
patient_Temperature and patient_temperature are different variables
Capital T vs lowercase t
Correct! The variable is defined as patient_Temperature (with capital T) but referenced as patient_temperature (lowercase t). Due to case sensitivity, Python treats these as two different variables, causing a NameError.
Python doesn't allow underscores in variable names
Should be patientTemperature
Python allows underscores in variable names. In fact, snake_case is the preferred style.
