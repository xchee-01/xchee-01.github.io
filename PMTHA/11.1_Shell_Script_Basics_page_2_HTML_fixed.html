11.1.4. Running Scripts (The Many Ways to Make Scripts Go!)

Method 1: The Dot-Slash Dance (./)

# The most common way ./hello_world.sh
Copied!

Mental Model: The ./ is like saying "Hey Linux, run the script that's RIGHT HERE in this folder!"

Method 2: The Full Path Marathon

# Works from anywhere /home/$USER/hello_world.sh
Copied!

Method 3: The Bash Bypass

# Skips permission checks bash hello_world.sh
Copied!

⚡ Quick Tip: This method is like having a master key - works even without execute permissions!

Method 4: The Source Sorcery

# Runs in current shell source hello_world.sh
Copied!
Learning Checkpoint
Which script execution method runs the script in the current shell environment, preserving variable changes?
./script.sh
Execute script in the current directory
Not quite. The ./ method runs the script in a new subshell, so variable changes won't persist in the current shell.
bash script.sh
Run script using bash command
Incorrect. The bash command also creates a new subshell, so variables set in the script won't be available after it completes.
source script.sh
Source the script in current shell
Correct! The `source` command runs the script in the current shell, allowing variables and environment changes to persist after the script completes.
/full/path/script.sh
Run script using full path
Not correct. Using the full path still runs the script in a new subshell, just like the ./ method.

Learning Checkpoint
You have a script without execute permissions. Which of the following commands will NOT work to run it?
bash myscript.sh
Run with bash command
Actually, this will work! The bash command reads and executes the script without needing execute permissions.
./myscript.sh
Run with dot-slash method
Correct! The `./` method requires execute permissions. Without them, you'll get a "Permission denied" error. The other methods bypass the execute permission requirement.
source myscript.sh
Source the script
This will work! Source reads and executes the script in the current shell without needing execute permissions.
sh myscript.sh
Run with sh command
This will work too! Like bash, the sh command reads and executes the script without needing execute permissions.

Lab Exercise 2: Build a Complete Script Development Pipeline

Objective: Create a professional script development and deployment workflow that automates script creation and management.
Instructions:

  2. Set up a personal bin directory for script deployment
  3. Configure PATH to make your scripts accessible from anywhere
  4. Test the complete workflow end-to-end

Part 1: Create the Script Development Tool

First, ensure you have a personal bin directory:

# Create your personal bin directory mkdir -p ~/bin # Verify it exists ls -la ~/bin
Copied!

Now create the mkscript tool:

# Create a script that helps make other scripts! cat > ~/bin/mkscript << 'EOF' #!/bin/bash # Script creator tool if [ $# -eq 0 ]; then echo "Usage: mkscript " echo "Creates a new bash script with proper shebang and permissions" exit 1 fi SCRIPT_NAME="$1" # Create the script with shebang echo '#!/bin/bash' > "$SCRIPT_NAME" echo '# Script: '"$SCRIPT_NAME" >> "$SCRIPT_NAME" echo '# Created: '"$(date)" >> "$SCRIPT_NAME" echo '# Author: '"$USER" >> "$SCRIPT_NAME" echo '' >> "$SCRIPT_NAME" echo '# Your code here' >> "$SCRIPT_NAME" # Make it executable chmod +x "$SCRIPT_NAME" echo "✅ Created executable script: $SCRIPT_NAME" echo "📝 Edit with: nano $SCRIPT_NAME" echo "🏃 Run with: ./$SCRIPT_NAME" EOF # Make mkscript executable chmod +x ~/bin/mkscript
Copied!

Part 2: Configure PATH

# Add ~/bin to PATH for current session export PATH="$HOME/bin:$PATH" # Verify PATH update echo $PATH | grep "$HOME/bin" # Make it permanent by adding to .bashrc echo 'export PATH="$HOME/bin:$PATH"' >> ~/.bashrc # Reload configuration source ~/.bashrc
Copied!

Part 3: Test Your Development Workflow

# Change to a different directory to test PATH cd /tmp # Use mkscript from anywhere! mkscript test_script.sh # Check what was created cat test_script.sh # Verify permissions ls -l test_script.sh # Run the new script ./test_script.sh
Copied!
Expected Results:
  • The mkscript command should work from any directory
  • New scripts should be created with proper shebang and execute permissions
  • Your PATH should permanently include ~/bin

Learning Checkpoint
What does the $# variable represent in the mkscript tool?
The process ID of the script
Current process identifier
Not correct. The process ID is stored in $$, not $#.
The number of command-line arguments passed
Count of parameters provided
Correct! $# contains the number of arguments passed to the script. In this case, it's used to check if the user provided a script name.
The exit status of the last command
Previous command's return code
Incorrect. The exit status is stored in $?, not $#.
The name of the script being run
Current script filename
Wrong. The script name is stored in $0, not $#.

11.1.6. Script Locations and PATH (Where Scripts Live)

Understanding PATH - Your Script's Address Book

PATH is like your phone's contact list - instead of memorizing everyone's number, you just use their name. Similarly, PATH lets you run scripts by name from anywhere!

# See your current PATH echo $PATH | tr ':' '\n'
Copied!
Learning Checkpoint
What does the PATH environment variable do in Linux?
Stores the current directory location
PATH = current working directory
Not quite. The current directory is stored in the PWD variable, not PATH.
Lists directories where executable programs are searched
PATH = search directories for commands
Correct! PATH is a colon-separated list of directories where Linux searches for executable commands and scripts when you type their name.
Shows the path to your home directory
PATH = home directory location
Incorrect. Your home directory path is stored in the HOME variable, not PATH.
Contains the history of visited directories
PATH = directory navigation history
That's not right. Directory history is managed by commands like pushd/popd, not the PATH variable.

Creating Your Personal Script Neighborhood

# Make your own script directory mkdir -p ~/bin # Check if it exists ls -la ~/bin # Add it to PATH (for this session) export PATH="$HOME/bin:$PATH" # Verify it worked echo $PATH | grep "$HOME/bin"
Copied!
Learning Checkpoint
After running export PATH="$HOME/bin:$PATH", what happens when you run a command?
Linux only looks in $HOME/bin for commands
All other directories are ignored
Not correct. The command adds $HOME/bin to the existing PATH, it doesn't replace it.
Linux searches $HOME/bin first, then other PATH directories
Prepending creates search priority
Correct! By prepending $HOME/bin to PATH, Linux will search this directory first before checking other directories in the PATH.
Linux searches other PATH directories first, then $HOME/bin
New directory has lowest priority
Incorrect. The order matters - directories at the beginning of PATH are searched first.
Linux removes all other directories from PATH
PATH is completely replaced
Wrong. The :$PATH at the end preserves all existing directories in PATH.

Making PATH Changes Permanent

# Add to ~/.bashrc for permanent PATH echo 'export PATH="$HOME/bin:$PATH"' >> ~/.bashrc # Reload configuration source ~/.bashrc
Copied!
Learning Checkpoint
You added a directory to PATH using export PATH="/new/dir:$PATH" but after restarting your terminal, the change is gone. What's the most likely reason?
The export command is broken
Export functionality is faulty
Not likely. The export command works fine, the issue is with persistence.
The PATH variable cannot be modified
PATH is read-only
Incorrect. PATH can definitely be modified - you just did it successfully!
The change wasn't saved to a shell configuration file
No persistence mechanism used
Correct! PATH modifications using export are only temporary for the current session. To make them permanent, you need to add the export command to a shell configuration file like ~/.bashrc.
Linux automatically resets PATH on restart
System security feature
Not true. Linux loads PATH from configuration files on startup, not from a reset mechanism.

Final Skills Check
You created a script called "backup.sh" in ~/scripts/ and want to run it from any directory without typing the full path. What's the correct sequence of commands?
chmod +x ~/scripts/backup.sh; export PATH="$PATH:~/scripts"
Make executable then add to PATH with tilde
Close, but the tilde (~) won't expand properly in PATH. Use $HOME instead.
export PATH="~/scripts:$PATH"; chmod +x backup.sh
Add to PATH first, then make executable
Two issues: tilde won't expand in PATH, and chmod needs the full path to the script.
chmod +x ~/scripts/backup.sh; export PATH="$PATH:$HOME/scripts"
Make executable then add to PATH with $HOME
Correct! First make the script executable with chmod +x, then add the directory to PATH. Use $HOME instead of ~ in PATH for proper expansion.
source ~/scripts/backup.sh; export PATH="$HOME/scripts"
Source the script then set PATH
Wrong approach. Source runs the script immediately, and the PATH export is missing the existing PATH.
