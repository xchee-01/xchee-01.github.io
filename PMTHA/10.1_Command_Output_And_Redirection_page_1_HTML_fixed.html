Linux I/O Redirection

Welcome to Linux I/O redirection! One of the most powerful features that makes Linux administrators productive is controlling where command output goes and input comes from. Think of redirection as your traffic control system for data flow.

Understanding Standard Streams and Output Redirection (>)

Understanding Standard Streams

Every Linux process has three "communication channels":

1. Standard Input (stdin) - File Descriptor 0

  • Where programs read input (usually keyboard)
  • The program's "ears"

2. Standard Output (stdout) - File Descriptor 1

  • Where programs send normal output (usually screen)
  • The program's "voice"

3. Standard Error (stderr) - File Descriptor 2

  • Where programs send error messages (also screen)
  • The program's "alarm bell"
Learning Checkpoint
What is the file descriptor number for standard output (stdout)?
0
File descriptor 0
Not correct. File descriptor 0 is for standard input (stdin), not standard output.
1
File descriptor 1
Correct! Standard output (stdout) uses file descriptor 1, stdin uses 0, and stderr uses 2.
2
File descriptor 2
That's not right. File descriptor 2 is for standard error (stderr), not standard output.
3
File descriptor 3
Incorrect. File descriptors 0, 1, and 2 are reserved for stdin, stdout, and stderr respectively. File descriptor 3 would be for the first user-opened file.

Learning Checkpoint
When a program sends an error message, which stream does it typically use?
stdin (file descriptor 0)
Standard input stream
Not correct. stdin is for input, not output. Programs read from stdin, they don't send messages to it.
stdout (file descriptor 1)
Standard output stream
Not quite. stdout is for normal output. Error messages have their own dedicated stream.
stderr (file descriptor 2)
Standard error stream
Correct! Error messages are sent to stderr (standard error), which is file descriptor 2. This allows errors to be handled separately from normal output.
stdlog (file descriptor 3)
Standard logging stream
Incorrect. There is no standard "stdlog" stream. The three standard streams are stdin (0), stdout (1), and stderr (2).

Lab Exercise 1: Stream Detective

As a system administrator, you need to understand how different streams work. Let's explore the difference between standard output and standard error streams.

Step 1: Observe Normal Output

# Run this command to see normal output ls /home
Copied!

Step 2: Trigger an Error

# Run this command to see error output ls /this_directory_does_not_exist
Copied!

Step 3: Prove They're Different Streams

# Redirect stdout only (errors still appear on screen) ls /home /this_does_not_exist > only_stdout.txt # Check what was captured cat only_stdout.txt
Copied!

Expected result:

Error message appears on screen: ls: cannot access '/this_does_not_exist': No such file or directory File contains only valid output from /home

Answer:

The error still appeared on screen because > only redirects stdout (file descriptor 1), not stderr (file descriptor 2). To capture both, you would need:

# Redirect both stdout and stderr ls /home /this_does_not_exist > output.txt 2>&1 # Or use the modern shorthand ls /home /this_does_not_exist &> output.txt
Copied!
Learning Checkpoint

Not correct. The > operator only redirects stdout, not stderr.

stdout is redirected, stderr remains on terminal
Correct! The > operator redirects only stdout. Error messages (stderr) still appear on the terminal screen.
Only errors go to output.txt
stderr is redirected to the file
Incorrect. The > operator redirects stdout, not stderr. To redirect stderr, you would use 2>.
Nothing is saved to output.txt
The command fails completely
Not right. Even if one path is invalid, the valid output from /home will still be saved to the file.

Output Redirection with > (The Overwriter)

The > operator redirects output from screen to file. Warning: It overwrites existing files!

# Save directory listing ls -la /etc > system_configs.txt # Check what was saved head -10 system_configs.txt
Copied!

Common Mistake:

echo "=== Server Report ===" > report.txt date > report.txt # Oops! First line gone!
Copied!
Learning Checkpoint
What happens to existing content when you use > to redirect output to a file?
Content is appended to the end
New content is added after existing content
Not correct. That's what >> does, not >. The single > overwrites.
Content is preserved and new data added
Both old and new content are kept
That's not right. The > operator doesn't preserve existing content.
Existing content is completely overwritten
All previous content is lost
Correct! The > operator overwrites any existing content in the file. Use >> to append instead.
An error occurs if file exists

Incorrect. The > operator will happily overwrite existing files without warning (unless noclobber is set).

Lab Exercise 2: System Report Generator

You've been asked to create a system report script, but the previous administrator left a broken script. Your task is to fix it so it creates a complete report without losing any information.

The Broken Script:

# WARNING: This script has a problem! echo "System Report - $(date)" > system_report.txt echo "=========================" > system_report.txt uname -a > system_report.txt df -h > system_report.txt free -h > system_report.txt # Check the result cat system_report.txt
Copied!

Expected output (what you should see):

System Report - [current date] ========================= [System information from uname] [Disk usage information from df] [Memory information from free]

Actual output (what the broken script produces):

[Only memory information from free -h command]

Answer:

The problem is that each > overwrites the file. Here's the fixed version:

# Fixed script - First line creates with > echo "System Report - $(date)" > system_report.txt # Subsequent lines append with >> echo "=========================" >> system_report.txt echo "" >> system_report.txt echo "SYSTEM INFO:" >> system_report.txt uname -a >> system_report.txt echo "" >> system_report.txt echo "DISK USAGE:" >> system_report.txt df -h >> system_report.txt echo "" >> system_report.txt echo "MEMORY:" >> system_report.txt free -h >> system_report.txt # View complete report cat system_report.txt
Copied!

Key Learning: Use > for the first line to create a fresh file, then >> for all subsequent lines to append without overwriting.

Learning Checkpoint
Why does the broken script only show memory information in the final file?
The free command overwrites all previous commands
The free command has special behavior
Not quite. It's not about the free command specifically, but about how redirection works.
Each > operator overwrites the file completely
Every use of > starts with an empty file
Correct! Each use of > overwrites the entire file. Only the last command's output (free -h) remains.
The script has syntax errors
Commands are not written correctly
Incorrect. The syntax is fine. The issue is with using > instead of >> for subsequent lines.
The uname and df commands failed
Only free -h succeeded
Not right. All commands likely succeeded, but their output was overwritten by subsequent redirections.

Golden Rule: First > creates, then >> appends!

Append Redirection with >> (The Friendly Adder)

The >> operator adds content to the end of files without destroying existing content. This is essential for log files, continuous monitoring, and building reports over time.

Basic Append Operations

# Create monitoring log echo "=== Daily Checks ===" > daily.log echo "Started: $(date)" >> daily.log # Simulate hourly checks echo "10:00 - CPU:" >> daily.log uptime >> daily.log echo "11:00 - Memory:" >> daily.log free -h | grep Mem >> daily.log echo "12:00 - Disk:" >> daily.log df -h | grep "/$" >> daily.log # View the complete log cat daily.log
Copied!
Learning Checkpoint
Which operator should you use to add new log entries to an existing log file without losing previous entries?
>
Single greater-than sign
Not correct. The > operator would overwrite the existing log file, losing all previous entries.
>>
Double greater-than sign
Correct! The >> operator appends to files, preserving existing content. The > operator would overwrite the file.
<
Less-than sign
Incorrect. The < operator is for input redirection, not output.
<<
Double less-than sign
Not right. The << operator is used for here documents, not for appending to files.

Common Use Cases for Append

1. Building Log Files

# Application log echo "[$(date)] Application started" >> app.log echo "[$(date)] Processing user request" >> app.log echo "[$(date)] Request completed successfully" >> app.log
Copied!

2. Collecting System Statistics

# Create header once echo "Timestamp,CPU_Load,Memory_Used" > system_stats.csv # Append data every minute (in a real script, this would be in a loop) echo "$(date +%s),$(uptime | awk -F'load average:' '{print $2}' | awk -F, '{print $1}'),$(free -m | grep Mem | awk '{print $3}')" >> system_stats.csv
Copied!

3. Combining Multiple Sources

# Start error collection echo "=== Error Summary ===" > all_errors.log # Append from different log files grep ERROR /var/log/syslog >> all_errors.log grep FAIL /var/log/auth.log >> all_errors.log grep WARNING /var/log/apache2/error.log >> all_errors.log
Copied!

Pro Tip: When writing scripts that run via cron, always use >> for logs. This ensures each run adds to the history rather than destroying it!

Learning Checkpoint
To create a new log file with a header and then add timestamped entries, which pattern is correct?
echo "Log" >> log.txt; date >> log.txt
Append both lines
This works but doesn't guarantee a clean start if log.txt already exists.
echo "Log" > log.txt; date > log.txt
Overwrite for both
Not correct. The second > overwrites the first line. Only the date would remain.
echo "Log" > log.txt; date >> log.txt
Create then append
Correct! Use > to create the file with the header, then >> to append additional entries without overwriting.
echo "Log" < log.txt; date < log.txt
Read from file
Incorrect. The < operator is for input, not output. This would try to read from the file.

Input Redirection with < (The File Reader)

The < operator tells commands to read from files instead of keyboard. This is powerful for automation and batch processing.

Basic Input Redirection

# Create a list cat > shopping.txt << EOF apples bananas chocolate EOF # Sort the list sort < shopping.txt # Count items wc -l < shopping.txt
Copied!
Learning Checkpoint

Modifies the original file
Not correct. The sort command doesn't modify the original file unless you redirect output back to it.
Reads content from shopping.txt and displays sorted output
Shows sorted results on screen
Correct! The < operator redirects the file content as input to the sort command, which then displays the sorted output to screen.
Creates a sorted copy called shopping.txt
Makes a new file with sorted content
Incorrect. Without output redirection, sort only displays results to screen.
Sorts files in the current directory

Not right. The sort command sorts text content, not directory listings.

Advanced Input Redirection

Processing Files with Loops

# Read and process each line while read line do echo "Processing: $line" done < shopping.txt

Lab Exercise 3: Config File Generator

You need to create configuration files for multiple servers based on a server list. This exercise demonstrates the power of input redirection for batch processing.

Step 1: Create the Server List

# Create a server list file with server details cat > servers.txt << EOF web01:192.168.1.10:webserver web02:192.168.1.11:webserver db01:192.168.1.20:database EOF # Verify the list cat servers.txt
Copied!

Step 2: Process the List with Input Redirection

# Read and process each server entry while IFS=: read -r hostname ip role do config="${hostname}.conf" # Create config file echo "# Configuration for $hostname" > "$config" echo "hostname = $hostname" >> "$config" echo "ip_address = $ip" >> "$config" echo "role = $role" >> "$config" # Add role-specific settings case $role in webserver) echo "port = 80" >> "$config" echo "document_root = /var/www/html" >> "$config" ;; database) echo "port = 3306" >> "$config" echo "data_directory = /var/lib/mysql" >> "$config" ;; esac echo "Created: $config" done < servers.txt # List created files ls *.conf
Copied!

Expected output:

Created: web01.conf Created: web02.conf Created: db01.conf web01.conf web02.conf db01.conf

Answer:

The script uses input redirection to feed the server list to a while loop. Key points:

  • IFS=: sets the field separator to colon
  • read -r hostname ip role splits each line into variables
  • done < servers.txt feeds the file to the loop
  • Each iteration creates a customized config file

To verify the configs were created correctly:

# Check one of the generated configs cat web01.conf
Copied!

Lab Exercise 4: Complete System Monitor

Create a comprehensive monitoring script that generates timestamped reports using all three redirection operators. This brings together everything you've learned.

Your Task: Create a monitoring script that:

  1. Creates a fresh report file (using >)
  2. Appends system information (using >>)
  3. Reads configuration from a file (using <)
# First, create a config file that lists what to monitor cat > monitor.conf << 'EOF' SYSTEM_INFO DISK_USAGE MEMORY_USAGE TOP_PROCESSES EOF # Create the monitoring script cat > monitor.sh << 'EOF' #!/bin/bash # System Monitor Script # Initialize report with timestamp echo "System Monitor Report - $(date)" > monitor_report.txt echo "================================" >> monitor_report.txt # Read config and generate appropriate sections while read section do case $section in SYSTEM_INFO) echo -e "\n[SYSTEM INFORMATION]" >> monitor_report.txt uname -a >> monitor_report.txt ;; DISK_USAGE) echo -e "\n[DISK USAGE]" >> monitor_report.txt df -h >> monitor_report.txt ;; MEMORY_USAGE) echo -e "\n[MEMORY USAGE]" >> monitor_report.txt free -h >> monitor_report.txt ;; TOP_PROCESSES) echo -e "\n[TOP 5 CPU PROCESSES]" >> monitor_report.txt ps aux --sort=-%cpu | head -6 >> monitor_report.txt ;; esac done < monitor.conf echo -e "\nReport generated at $(date)" >> monitor_report.txt echo "Report saved to monitor_report.txt" EOF # Make script executable and run it chmod +x monitor.sh ./monitor.sh # View the report cat monitor_report.txt
Copied!

Expected output structure:

System Monitor Report - [current date/time] ================================ [SYSTEM INFORMATION] [system details from uname] [DISK USAGE] [disk usage information] [MEMORY USAGE] [memory statistics] [TOP 5 CPU PROCESSES] [process list] Report generated at [current date/time]

Answer:

This script demonstrates all three redirection operators working together:

  • > creates the initial report file with a timestamp header
  • >> appends each monitoring section without overwriting
  • < reads the configuration file to determine what to monitor

The beauty of this approach is flexibility - you can change what gets monitored by simply editing monitor.conf!

Summary: I/O Redirection Mastery

Congratulations! You've mastered the fundamental I/O redirection operators in Linux. Let's review what you've learned:

The Three Essential Operators

  1. Output Redirection (>)
    • Creates or overwrites files with command output
    • Use for starting fresh logs or reports
    • Remember: It's destructive - existing content is lost!
  2. Append Redirection (>>)
    • Adds output to existing files without overwriting
    • Perfect for log files and continuous monitoring
    • Golden rule: First > creates, then >> appends
  3. Input Redirection (<)
    • Feeds file content as input to commands
    • Essential for batch processing and automation
    • Works perfectly with loops for processing lists

Key Concepts to Remember

Standard Streams:

  • stdin (0) - Standard input
  • stdout (1) - Standard output
  • stderr (2) - Standard error

Best Practices:

  • Always use > for the first line when creating reports
  • Use >> for all subsequent additions to preserve content
  • Combine < with loops for powerful batch processing
  • Remember that > only redirects stdout, not stderr

Real-World Applications

These operators form the foundation of Linux automation and scripting:

  • System Monitoring: Automated reports and alerts
  • Log Management: Collecting and organizing system logs
  • Batch Processing: Processing lists of servers, files, or users
  • Data Pipeline: Building complex data processing workflows
