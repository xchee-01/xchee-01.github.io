MODULE 2: Mastering chmod and Advanced Permissions

Mission: chmod - Your Permission Swiss Army Knife

Now comes the fun part—actually CHANGING permissions! The chmod command (think "change mode") is your Swiss Army knife for permission management. You have two powerful ways to use it:

Method 1: Symbolic Mode (Human-Friendly)

This method uses letters and symbols—perfect when you're making specific changes:

# The formula: WHO + WHAT + WHICH # WHO: u (user/owner), g (group), o (others), a (all) # WHAT: + (add), - (remove), = (set exactly) # WHICH: r (read), w (write), x (execute) # Add execute permission for owner user@hostname:~$ chmod u+x script.sh # Remove write permission from others (security fix!) user@hostname:~$ chmod o-w sensitive_file.txt # Set exact permissions: owner can do everything, others read-only user@hostname:~$ chmod u=rwx,go=r important_doc.txt
Copied!

Pro Tip: You can combine multiple changes with commas: chmod u+x,g+w,o-r file.txt

🔧 Fix-It Lab: Make That Script Run!

Learning Checkpoint
Remember our broken script? Let's fix it. After running chmod u+x mystery_script.sh, what will the permissions look like?
# Check current permissions user@hostname:~/permission_lab$ ls -la mystery_script.sh -rw-rw-r-- 1 username username 42 Oct 25 14:30 mystery_script.sh # Your mission: Make it executable for the owner user@hostname:~/permission_lab$ chmod u+x mystery_script.sh # Verify your fix user@hostname:~/permission_lab$ ls -la mystery_script.sh -rwxrw-r-- 1 username username 42 Oct 25 14:30 mystery_script.sh # ↑ Look! The x appeared! # Test your success user@hostname:~/permission_lab$ ./mystery_script.sh 🎉 Script is running!
-rw-rw-rw-
Adds write permission for others
Not correct. The command u+x adds execute permission for the user/owner, not write permission for others.
-rwxrw-r--
Adds execute permission for the owner
Correct! The u+x adds execute (x) permission for the user/owner, changing the first permission group from rw- to rwx.
-rwxrwxrwx
Adds execute permission for everyone
That's not right. The 'u' in u+x specifically targets only the user/owner, not the group or others.
-r-xrw-r--
Removes write permission and adds execute
Incorrect. The + operator adds permissions without removing existing ones. The command preserves the existing rw- and adds x.

🎊 Achievement Unlocked: Script Surgeon! You've successfully performed permission surgery!

Method 2: Numeric Mode (The Pro Method)

Once you go numeric, you never go back! This method uses octal numbers and sets ALL permissions at once:

Permission Values: r (read) = 4 w (write) = 2 x (execute) = 1 Add them up for each group: rwx = 4+2+1 = 7 (full access) rw- = 4+2+0 = 6 (read & write) r-x = 4+0+1 = 5 (read & execute) r-- = 4+0+0 = 4 (read only) --- = 0+0+0 = 0 (no access)
Copied!

Common Permission Patterns (The "Greatest Hits")

Here are the permission patterns you'll use 90% of the time:

# 755 - Standard for executables and directories # Owner: everything, Others: read & traverse user@hostname:~$ chmod 755 my_program.sh user@hostname:~$ chmod 755 public_directory/ # 644 - Standard for regular files # Owner: read/write, Others: read-only user@hostname:~$ chmod 644 readme.txt # 600 - Private files (SSH keys, passwords) # Owner: read/write, Others: no access user@hostname:~$ chmod 600 ~/.ssh/id_rsa # 777 - DANGER! Full access for everyone # Only use for temporary directories user@hostname:~$ chmod 777 /tmp/shared_workspace/
Copied!

⚠️ Security Alert: Never use 777 on sensitive files! It's like leaving your house keys under the doormat with a big sign saying "KEY HERE"!

🌟 Real-World Scenario: Web Server Setup

Let's practice with a realistic web server setup:

# Create a mini web project user@hostname:~$ mkdir my_website && cd my_website user@hostname:~/my_website$ mkdir images css js user@hostname:~/my_website$ touch index.html style.css script.js user@hostname:~/my_website$ touch .htaccess config.php # Set appropriate permissions user@hostname:~/my_website$ chmod 755 . images/ css/ js/ # Directories user@hostname:~/my_website$ chmod 644 index.html style.css # Public files user@hostname:~/my_website$ chmod 600 config.php # Contains passwords! user@hostname:~/my_website$ chmod 644 .htaccess # Apache needs to read this # Verify your security setup user@hostname:~/my_website$ ls -la
Copied!

🔍 Self-Check Questions:

Learning Checkpoint
Why do directories need execute permission?
To run scripts inside them
Execute permission allows running programs in the directory
Not quite. Execute permission on a directory doesn't affect running scripts inside it - that depends on the script's own permissions.
To traverse/enter the directory
Execute permission allows accessing files inside the directory
Correct! For directories, execute permission means "traverse" - the ability to cd into it or access files inside it.
To delete the directory
Execute permission controls directory deletion
Incorrect. Deleting a directory depends on write permissions in its parent directory, not execute permission on the directory itself.
They don't need it
Execute permission is only for files
Wrong. Directories absolutely need execute permission for users to access their contents. Without it, you can't cd into the directory or access any files inside.
Learning Checkpoint
What would happen if config.php was world-readable (644 instead of 600)?
Nothing - it's fine
World-readable is normal for web files
Dangerous thinking! Config files often contain database passwords and API keys that should never be world-readable.
Security risk - exposes passwords
Anyone on the system could read database credentials
Correct! Config files typically contain sensitive information like database passwords. World-readable permissions would expose these credentials to any user on the system.
The website would break
PHP requires config files to be private
Not true. PHP will still read world-readable files. The issue is security, not functionality.
Better performance
More open permissions improve speed
Completely wrong! Permission levels have no impact on performance, and looser permissions are never better for security.
Learning Checkpoint
Why might a 777 permission cause Apache to ignore .htaccess?
777 corrupts the file
Full permissions damage file integrity
No, permissions don't change file contents. The issue is with Apache's security checks.
Security feature - prevents tampering
Apache ignores world-writable config files for safety
Correct! Apache has a security feature that ignores .htaccess files if they're world-writable (777) to prevent malicious users from modifying server configuration.
Apache can't read 777 files
Full permissions block Apache access
Wrong. Apache can read 777 files just fine. It chooses to ignore them as a security precaution.
It's a myth - 777 works fine
There's no issue with 777 permissions
Definitely not a myth! This is a real Apache security feature that protects against configuration tampering.

Advanced Permission Tricks

Special Permissions Preview

Linux has some special permission bits that add superpowers:

# Make a directory where anyone can create files, but only delete their own user@hostname:~$ mkdir shared_workspace user@hostname:~$ chmod 1777 shared_workspace # The '1' is the sticky bit! # See the sticky bit in action user@hostname:~$ ls -ld shared_workspace drwxrwxrwt 2 username username 4096 Oct 25 15:00 shared_workspace # ↑ 't' indicates sticky bit
Copied!

🔧 Troubleshooting Lab: Fix Common Permission Errors

Practice fixing these common permission problems:

Learning Checkpoint
Problem 1: Script downloaded from internet won't run
# Problem 1: Script downloaded from internet won't run user@hostname:~$ wget https://example.com/useful_script.sh user@hostname:~$ ./useful_script.sh bash: ./useful_script.sh: Permission denied # Your fix: _______________
sudo ./useful_script.sh
Run with administrator privileges
Dangerous! Never run untrusted scripts with sudo. The issue is missing execute permission, not privileges.
chmod +x useful_script.sh
Add execute permission to the script
Correct! Downloaded files typically don't have execute permission for security. Adding it with chmod +x allows the script to run.
chmod 777 useful_script.sh
Give full permissions to everyone
Overkill! While this would work, 777 is unnecessarily permissive. Use chmod +x or chmod 755 instead.
bash useful_script.sh
Run through bash interpreter
This works as a workaround but doesn't fix the permission issue. The script still won't run with ./
Learning Checkpoint
Problem 2: Can't edit file you created yesterday
# Problem 2: Can't edit file you created yesterday user@hostname:~$ echo "new line" >> myfile.txt bash: myfile.txt: Permission denied # Investigate and fix: _______________
chmod 777 myfile.txt
Make it fully accessible
Too permissive! First check with ls -la to see current permissions, then use appropriate chmod like u+w.
ls -la myfile.txt, then chmod u+w
Check permissions first, then add write for owner
Perfect approach! Always investigate first with ls -la to understand the problem, then fix with the minimum necessary permissions.
sudo echo "new line" >> myfile.txt
Use admin privileges
Won't work! The >> redirection happens before sudo, so you'll still get permission denied. Plus, using sudo for your own files is wrong.
rm myfile.txt && touch myfile.txt
Delete and recreate the file
This would lose all content! Never delete a file just to fix permissions.
Learning Checkpoint
Problem 3: Web server can't read your HTML file
# Problem 3: Web server can't read your HTML file # Apache error log shows: "Permission denied" # Your approach: _______________
chmod 777 index.html
Give everyone full access
Never use 777 for web files! This creates security vulnerabilities. Use 644 for files and 755 for directories.
chmod 644 index.html && chmod 755 .
Set proper web permissions for file and directory
Excellent! Web files need 644 (owner write, others read) and directories need 755 (with execute for traversal). This gives Apache read access safely.
chown apache:apache index.html
Change ownership to Apache user
While this might work, changing ownership isn't the first solution. Proper permissions (644) should allow Apache to read without ownership change.
Restart Apache service
Maybe Apache needs a restart
Won't help if it's a permission issue. Apache doesn't cache file permissions, so restarting won't fix permission denied errors.

Permission Best Practices Checklist

Before we wrap up, here's your security checklist:

  • ☐ Principle of Least Privilege: Give minimum necessary permissions
  • ☐ Regular Audits: Run find . -perm 777 to find overly permissive files
  • ☐ Script Security: Never leave scripts world-writable
  • ☐ Sensitive Files: Always use 600 or 640 for files with passwords
  • ☐ Directory Traversal: Directories need 'x' for users to access files inside
  • ☐ Version Control: .git directories should never be world-readable on web servers
