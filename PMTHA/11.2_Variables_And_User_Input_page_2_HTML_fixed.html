11.2.5. Command Line Arguments and Validation

Command line arguments make your scripts flexible and reusable. Learn how to accept, validate, and process arguments professionally.

Understanding Positional Parameters

Bash provides special variables to access command line arguments:

  • $0 - The script name itself
  • $1 - First argument
  • $2 - Second argument
  • $# - Total number of arguments
  • $@ - All arguments as separate words
  • $* - All arguments as a single string
Learning Checkpoint
Basic Example:
#!/bin/bash # greeter.sh echo "Script name: $0" echo "Hello $1! Welcome to $2." echo "You provided $# arguments."
Copied!
What will be the output when you run: ./greeter.sh Alice "Linux World"?
Script name: ./greeter.sh
Hello Alice! Welcome to Linux World.
You provided 2 arguments.
The script correctly displays all the positional parameters.
Correct! $0 is the script name, $1 is "Alice", $2 is "Linux World", and $# shows 2 total arguments.
Script name: greeter.sh
Hello $1! Welcome to $2.
You provided $# arguments.
The variables remain as literal text.
Not quite. Bash substitutes variables with their values when executing the script.
Error: insufficient arguments
The script fails because we didn't provide enough arguments.
The script doesn't check for arguments, so it will run even if arguments are missing. Unset variables just expand to empty strings.

Validating Arguments

Professional scripts always validate their inputs to prevent errors and provide helpful feedback:

Learning Checkpoint
#!/bin/bash # Always validate arguments if [ $# -lt 2 ]; then echo "Error: Insufficient arguments" echo "Usage: $0 " exit 1 fi echo "Processing $1 -> $2"
Copied!
What does the condition [ $# -lt 2 ] check for?
If fewer than 2 arguments were provided
The script requires at least 2 arguments to run properly.
Correct! The -lt operator means "less than", so this checks if the number of arguments ($#) is less than 2.
If exactly 2 arguments were provided
The script checks for precisely 2 arguments.
Not quite. To check for exactly 2 arguments, you would use [ $# -eq 2 ] instead.
If more than 2 arguments were provided
The script checks for too many arguments.
Incorrect. To check for more than 2 arguments, you would use [ $# -gt 2 ] instead.

Best Practice: Always validate user input and provide helpful usage messages. This makes your scripts more professional and user-friendly.

11.2.6. Interactive Input with 'read' Command

Create conversational scripts that interact with users in real-time. The read command enables dynamic user interaction and input validation.

Basic Read Operations

Learning Checkpoint
Basic Read Examples:
echo "What's your name?" read user_name echo "Hello, $user_name!" # With prompt read -p "Enter your favorite distro: " distro echo "Great choice: $distro"
Copied!
What does the -p flag do in the read command?
Displays a prompt before reading input
The -p flag combines the prompt and read in one line.
Correct! The -p flag lets you specify a prompt string that appears before the user types their input.
Reads input as a password (hidden)
The -p flag hides the typed characters.
Not quite. To hide input (for passwords), you use the -s flag, not -p.
Pauses execution for user confirmation
The -p flag creates a pause in the script.
Incorrect. While read does pause for input, the -p flag specifically adds a prompt message.

Advanced Read Features

The read command supports many useful options for different scenarios:

Learning Checkpoint
# Password input (hidden) read -s -p "Enter password: " password echo # Timeout read -t 5 -p "Continue? (Y/n): " response # Single character read -n 1 -p "Press any key..." # Default value read -p "Enter backup location [/backup]: " backup_dir backup_dir=${backup_dir:-/backup}
Copied!
What happens if the user doesn't respond within 5 seconds to the timeout read command?
The script continues with an empty response variable
The read command times out and execution continues.
Correct! After the timeout, read returns with a non-zero exit status and the variable remains empty or unchanged.
The script terminates with an error
The timeout causes the script to exit.
Incorrect. The script continues execution; it doesn't terminate on timeout.
The default value "Y" is automatically used
The timeout triggers a default response.
Not quite. The timeout doesn't set a default value; you need to handle that separately in your script logic.

Input Validation Techniques

Always validate user input to ensure your scripts behave correctly:

Learning Checkpoint
# Validate numeric input while true; do read -p "Enter port (1-65535): " port if [[ "$port" =~ ^[0-9]+$ ]] && [ "$port" -ge 1 ] && [ "$port" -le 65535 ]; then break else echo "❌ Invalid port. Try again." fi done # Yes/No confirmation read -p "Delete files? (yes/no): " confirm if [[ "$confirm" != "yes" ]]; then echo "Operation cancelled." exit 0 fi
Copied!
What does the regex pattern ^[0-9]+$ validate?
The input contains only digits (0-9)
^ means start, [0-9]+ means one or more digits, $ means end.
Correct! This pattern ensures the entire string consists of only numeric digits from start to finish.
The input starts with a digit
The pattern checks if the first character is a number.
Not quite. The $ at the end means the pattern must match the entire string, not just the beginning.
The input is between 1 and 65535
The pattern validates the port range.
Incorrect. The regex only checks if it's a number; the range validation is done separately with -ge and -le.

11.2.7. Advanced Input Handling Techniques

Learn professional patterns that combine multiple input sources for maximum flexibility in your scripts.

The Professional Configuration Pattern

This pattern provides multiple ways to configure scripts, making them suitable for both interactive use and automation:

Learning Checkpoint
#!/bin/bash # Flexible configuration # Priority: CLI args > Env vars > Interactive > Defaults get_config() { local cli_value=$1 local env_var=$2 local prompt=$3 local default=$4 # CLI argument if [ -n "$cli_value" ]; then echo "$cli_value" return fi # Environment variable if [ -n "${!env_var}" ]; then echo "${!env_var}" return fi # Interactive input if [ -t 0 ]; then read -p "$prompt [$default]: " input echo "${input:-$default}" return fi # Default echo "$default" } # Usage server=$(get_config "$1" "APP_SERVER" "Enter server" "localhost") port=$(get_config "$2" "APP_PORT" "Enter port" "8080")
Copied!
What is the configuration priority order in this pattern?
CLI args → Environment vars → Interactive → Defaults
Command line arguments have the highest priority.
Correct! This pattern gives users maximum control: they can override settings via CLI, use environment variables for automation, interact when needed, or fall back to defaults.
Defaults → Interactive → Environment vars → CLI args
Defaults have the highest priority.
Incorrect. The function checks CLI arguments first, giving them highest priority, not defaults.
Environment vars → CLI args → Defaults → Interactive
Environment variables override command line arguments.
Not quite. CLI arguments should have highest priority to allow users to override any configuration.

Pro Tip: This configuration pattern is used in many professional tools. It provides flexibility for different use cases: automation (CLI/env), interactive use, and sensible defaults.
