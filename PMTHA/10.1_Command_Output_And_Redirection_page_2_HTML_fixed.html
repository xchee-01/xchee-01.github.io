Redirection Combos

Separating stdout and stderr

# Run command with mixed output ls /etc /fake_directory # Separate streams into different files ls /etc /fake_directory > good.txt 2> errors.txt # Check results echo "=== STDOUT ===" && head -5 good.txt echo "=== STDERR ===" && cat errors.txt
Copied!
Learning Checkpoint
What does the command ls /etc /fake_directory > good.txt 2> errors.txt accomplish?
Writes all output to both good.txt and errors.txt
Both files receive identical content.
Not quite. The command uses different redirection operators for different purposes.
Writes standard output to good.txt and error messages to errors.txt
Separates the two output streams into different files.
Correct! The > redirects stdout (file descriptor 1) to good.txt, while 2> redirects stderr (file descriptor 2) to errors.txt, effectively separating the two output streams.
Writes only errors to good.txt and ignores standard output
Standard output is discarded.
That's not right. The command handles both output streams, not just errors.
Creates two identical copies of the output
Duplicates all output into two files.
Incorrect. The command separates different types of output, not duplicates them.

Combining Streams with 2>&1

# WRONG - Order matters! ls /etc /fake 2>&1 > output.txt # RIGHT - Redirect stdout first ls /etc /fake > output.txt 2>&1 # Modern syntax ls /etc /fake &> output.txt
Copied!

Memory Trick: 2>&1 means "stderr goes where stdout is currently going"

Learning Checkpoint
Why does ls /etc /fake 2>&1 > output.txt NOT work as expected?
The syntax is invalid
The command will produce a syntax error.
The syntax is valid, but it doesn't do what you might expect.
stderr is redirected to the terminal, not the file
Order of operations causes unexpected behavior.
Correct! When 2>&1 is executed first, stderr is redirected to where stdout is currently going (the terminal). Then > output.txt redirects only stdout to the file, leaving stderr still going to the terminal.
The command will produce an error
It will fail to execute.
The command executes without error, but doesn't redirect as intended.
It only redirects stdout, ignoring stderr
stderr is not redirected at all.
Not quite. The command does attempt to redirect stderr, but to the wrong location.

The Black Hole: /dev/null 🕳️

# Discard errors only find / -name "*.conf" 2> /dev/null | head -10 # Run silently noisy_command &> /dev/null
Copied!
Learning Checkpoint
What is the purpose of /dev/null in Linux?
It's a temporary storage location
Files are stored temporarily before deletion.
No, /dev/null doesn't store anything at all.
It's a special file that discards all data written to it
Acts as a data "black hole".
Correct! /dev/null is a special device file that discards all data written to it, effectively acting as a "black hole" for unwanted output.
It's a backup location for deleted files
Similar to the Recycle Bin in Windows.
Incorrect. /dev/null immediately discards data, with no possibility of recovery.
It's a network interface
Used for network null routing.
That's not right. /dev/null is a special device file, not a network interface.

Here Documents - Multi-line Magic

Here documents (<<) embed multi-line content directly in scripts.

Basic Here Document

cat << EOF > welcome.txt Welcome to Linux! Remember: - Always make backups - Check logs regularly - Coffee helps ☕ Have a great day! EOF
Copied!
Learning Checkpoint
What does EOF represent in a here document?
End Of File command
A built-in command to end file operations.
No, EOF is not a command but a delimiter string.
A delimiter that marks the start and end of the here document
Can be any string of your choice.
Correct! EOF is a delimiter (it can be any string) that marks where the here document starts and ends. The same delimiter must be used at both the beginning and end.
Error Output File
Redirects errors to a file.
Incorrect. EOF is just a delimiter string, not related to error handling.
A required keyword that cannot be changed
Must always use EOF.
Not true. You can use any string as the delimiter, not just EOF.

With Variables

USER_NAME="Alice" DEPT="Engineering" cat << EOF > user_welcome.txt Hello $USER_NAME! Welcome to $DEPT department. Your home: $HOME Today is: $(date +%A) EOF
Copied!

Literal Here Documents

# Quote delimiter to prevent expansion cat << 'SCRIPT' > backup.sh #!/bin/bash BACKUP_DIR="/backup/$(date +%Y%m%d)" SOURCE_DIR="$1" mkdir -p "$BACKUP_DIR" rsync -av "$SOURCE_DIR" "$BACKUP_DIR/" SCRIPT chmod +x backup.sh
Copied!
Learning Checkpoint
What's the difference between << EOF and << 'EOF' in here documents?
There is no difference
Both behave exactly the same.
There is a significant difference in how they handle content.
Single quotes make the delimiter case-sensitive
EOF and eof would be different with quotes.
That's not the purpose of the quotes.
Single quotes prevent variable expansion in the content
Creates a literal here document.
Correct! Quoting the delimiter (like 'EOF') creates a literal here document where variables and command substitutions are NOT expanded, preserving the literal text.
Single quotes allow special characters in the delimiter
Enables using spaces or symbols in delimiter.
No, quotes affect content handling, not delimiter syntax.

Lab Exercise 4: Log Analysis Pipeline

Setup Test Data

cat << 'LOGS' > access.log [2024-01-15 10:15:23] INFO: User login [2024-01-15 10:16:45] ERROR: Database failed [2024-01-15 10:17:02] INFO: Page served [2024-01-15 10:18:33] WARNING: High memory [2024-01-15 10:19:45] ERROR: File not found LOGS
Copied!

Build Analysis Pipeline

# Extract severity levels grep "ERROR" access.log > errors.log grep "WARNING" access.log > warnings.log grep "INFO" access.log > info.log # Create report echo "Log Report - $(date)" > report.txt echo "==================" >> report.txt echo "Errors: $(wc -l < errors.log)" >> report.txt echo "Warnings: $(wc -l < warnings.log)" >> report.txt echo "Info: $(wc -l < info.log)" >> report.txt # Add error details echo "" >> report.txt echo "Error Details:" >> report.txt cat errors.log >> report.txt # Create email summary cat << EOF > email.txt To: admin@company.com Subject: Daily Log Analysis $(cat report.txt) Automated report EOF cat email.txt
Copied!
Learning Checkpoint
In the command echo "Errors: $(wc -l < errors.log)" >> report.txt, what does the < operator do?
It compares the word count with errors.log
Performs a comparison operation.
No, < is not a comparison operator in this context.
It redirects the content of errors.log as input to wc -l
Provides file content as stdin.
Correct! The < operator redirects the content of errors.log as standard input to the wc -l command, which then counts the number of lines.
It appends wc output to errors.log
Adds line count to the file.
Incorrect. The < operator reads from files, it doesn't write to them.
It creates a backup of errors.log
Preserves original file content.
That's not what the < operator does.

Advanced Challenge: Log Monitor Script

#!/bin/bash LOG_FILE="app.log" ERROR_FILE="errors.log" NORMAL_FILE="normal.log" MAX_SIZE=1048576 # 1MB # Rotate function rotate_logs() { for file in "$ERROR_FILE" "$NORMAL_FILE"; do if [ -f "$file" ] && [ $(stat -c%s "$file") -gt $MAX_SIZE ]; then mv "$file" "${file}.$(date +%Y%m%d_%H%M%S)" fi done } # Monitor loop tail -f "$LOG_FILE" | while read line do rotate_logs if echo "$line" | grep -q "ERROR\|CRITICAL"; then echo "$line" >> "$ERROR_FILE" else echo "$line" >> "$NORMAL_FILE" fi done
Copied!
Learning Checkpoint
What does tail -f "$LOG_FILE" do in the monitoring script?
Displays the last 10 lines of the log file once
Shows end of file and exits.
That would be just `tail` without the -f flag.
Continuously follows the log file, showing new lines as they're added
Real-time monitoring mode.
Correct! The -f flag makes tail "follow" the file, continuously monitoring it for new content and displaying new lines as they're appended to the file.
Filters the log file for specific patterns
Searches for matching lines.
No, tail -f doesn't filter content, it shows all new lines.
Creates a backup of the log file
Preserves log content.
Incorrect. tail -f reads and displays content, it doesn't create backups.

Quick Reference Card

# Redirect stdout command > file.txt # Create/overwrite command >> file.txt # Append # Redirect stderr command 2> errors.txt # Errors only command 2>> errors.txt # Append errors # Combine streams command > output.txt 2>&1 # Both to same file command &> output.txt # Modern syntax command > good.txt 2> bad.txt # Separate files # Input redirection command < input.txt # Read from file command << EOF # Here document content EOF # Discard output command > /dev/null # Discard stdout command 2> /dev/null # Discard stderr command &> /dev/null # Discard all
Copied!
Learning Checkpoint
Which command appends both stdout and stderr to a file called output.log?
command > output.log 2>&1
Redirects both streams to file.
Close, but this overwrites the file instead of appending.
command >> output.log 2>&1
Appends both streams to file.
Correct! The >> appends stdout to output.log, and 2>&1 redirects stderr to the same place as stdout, resulting in both streams being appended to the file.
command &> output.log
Modern syntax for both streams.
This redirects both streams but overwrites instead of appending.
command 2>> output.log
Appends error output.
This only appends stderr, not both streams.

It sets DEBUG to false if it's currently true

Provides a default value.

Tests equality.
That's not what this syntax does.

Makes DEBUG available to child processes.

Final Challenge
To create a script that logs stdout to normal.log, stderr to errors.log, and also saves a combined copy to all.log, which approach would work?
command > normal.log 2> errors.log > all.log
Multiple redirections in sequence.
This doesn't work - you can't redirect stdout twice like this.
command > normal.log 2> errors.log; command &> all.log
Run command twice.
This runs the command twice, which may produce different results.
command 2>&1 | tee all.log > normal.log 2> errors.log
Use tee with pipes.
This combines streams before tee, preventing separation.
command > >(tee normal.log >> all.log) 2> >(tee errors.log >> all.log)
Process substitution with tee.
Correct! Option D uses process substitution with tee to simultaneously write stdout to normal.log while appending to all.log, and stderr to errors.log while also appending to all.log, achieving all three requirements in one command.
