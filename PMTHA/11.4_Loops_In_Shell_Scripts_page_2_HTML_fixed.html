while Loops - The Persistent Guardians

Understanding while Loops

Think of while loops as that friend who keeps asking "Are we there yet?" Perfect for:

  • Monitoring system health
  • Reading files line by line
  • Waiting for conditions
  • Creating infinite monitors
Learning Checkpoint
Which of the following is NOT a typical use case for while loops in shell scripts?
Monitoring system health continuously
A common use case for while loops
Not quite. Monitoring system health continuously is actually a perfect use case for while loops, as they can run indefinitely checking system status.
Reading files line by line
Another typical while loop application
Incorrect. Reading files line by line is one of the most common uses of while loops in shell scripting.
Iterating through a fixed list of items
Better suited for other loop types
Correct! When you have a fixed list of items, a for loop is more appropriate. While loops are better for conditions that may change or when the number of iterations is unknown.
Waiting for specific conditions to be met
Classic while loop scenario
That's not right. Waiting for conditions is exactly what while loops excel at - they continue running until a condition becomes false.

Real-World System Monitor

#!/bin/bash # system_health_monitor.sh CPU_THRESHOLD=80 MEM_THRESHOLD=90 while true do cpu=$(top -bn1 | grep "Cpu" | awk '{print $2}' | cut -d'%' -f1) mem=$(free | grep Mem | awk '{print int($3/$2 * 100)}') echo "CPU: ${cpu}% | RAM: ${mem}%" if [ "$cpu" -gt "$CPU_THRESHOLD" ]; then echo "HIGH CPU!" fi sleep 5 done
Copied!
Learning Checkpoint

That's not right. The if condition checks if CPU > 80%, and 85% exceeds this threshold, so the alert will be displayed.

File Processing Line by Line

#!/bin/bash # log_analyzer.sh failed_logins=0 while IFS= read -r line do if echo "$line" | grep -q "authentication failure"; then ((failed_logins++)) fi done < /var/log/auth.log echo "Failed logins: $failed_logins"
Copied!
Learning Checkpoint
What does 'IFS= read -r line' accomplish in the file processing script?
It reads the file in binary mode
Not related to binary mode
Incorrect. The read command always reads text. Binary mode is not a concept in shell's read command.
It preserves leading/trailing whitespace and prevents backslash interpretation
IFS= and -r work together for exact reading
Correct! IFS= prevents trimming of whitespace, and -r prevents backslash from being interpreted as an escape character, ensuring the line is read exactly as it appears in the file.
It converts all text to uppercase
No case conversion happening
Not correct. The read command doesn't perform any case conversion. The text is read as-is from the file.
It reads the entire file at once
read processes one line at a time
That's not right. The read command reads one line at a time, which is why it's used in a while loop to process files line by line.

Loop Control - Master the Flow

break and continue

  • break: Exit loop completely
  • continue: Skip to next iteration
Learning Checkpoint
What is the difference between 'break' and 'continue' in shell loops?
break pauses the loop, continue resumes it
Not how these commands work
Incorrect. Neither command pauses or resumes - they control the flow of execution within the loop.
break exits the loop, continue skips to the next iteration
Fundamental loop control commands
Correct! break completely exits the loop and continues with code after the loop, while continue skips the rest of the current iteration and starts the next one.
break skips one iteration, continue exits the loop
These are reversed
Not quite. You have the functions reversed. Break exits, continue skips to the next iteration.
They both do the same thing
They have different functions
That's not right. Break and continue have very different behaviors in controlling loop execution.

break Example: Smart Scanner

#!/bin/bash # virus_scanner.sh for dir in /tmp /var/tmp /home/*/Downloads do for file in "$dir"/* do if grep -q "VIRUS_SIGNATURE" "$file" 2>/dev/null; then echo "THREAT DETECTED: $file" break 2 # Exit both loops fi done done
Copied!
Learning Checkpoint
What does 'break 2' do in the virus scanner script?
Breaks the inner loop only
The '2' has special meaning
Not quite. The number after break specifies how many nested loop levels to exit. break 2 exits more than just the inner loop.
Breaks both the inner and outer loops
Exits 2 levels of nested loops
Correct! break 2 exits two levels of loops - both the inner file loop and the outer directory loop, completely stopping the scan when a threat is found.
Breaks the script execution entirely
break doesn't exit the script
Incorrect. Break only exits loops, not the entire script. To exit a script, you would use the exit command.
Waits 2 seconds before breaking
The number isn't a time delay
That's not right. The number after break indicates how many loop levels to exit, not a time delay.

continue Example: Smart Backup

#!/bin/bash # selective_backup.sh for user_home in /home/* do username=$(basename "$user_home") # Skip system directories if [ "$username" = "lost+found" ]; then continue fi # Skip inactive users if ! lastlog -u "$username" | grep -q "20"; then continue fi echo "Backing up: $username" # Backup code here done
Copied!
Learning Checkpoint
In the selective backup script, which users will be backed up?
All users in /home directory
There are filters applied
Not correct. The script has two continue statements that skip certain users based on specific conditions.
Only the lost+found directory
Check the continue logic
Incorrect. The script specifically skips lost+found with a continue statement, so it won't be backed up.
Active users excluding system directories
Users with recent activity (containing "20" in lastlog)
Correct! The script backs up only users who: 1) are not system directories like lost+found, and 2) have "20" in their lastlog output (indicating recent activity, likely year 20xx).
Only users whose names contain "20"
The grep checks lastlog output, not username
That's not right. The grep command searches for "20" in the lastlog output (which shows login times), not in the username itself.

Lab Exercise 2: Selective File Processor

You need to create a script that processes log files in a directory but skips certain files based on specific criteria. This exercise demonstrates the power of the continue statement for selective processing.

#!/bin/bash # selective_file_processor.sh # Process log files but skip certain ones log_dir="/var/log" processed=0 skipped=0 for logfile in "$log_dir"/*.log do filename=$(basename "$logfile") # Skip if file is empty if [ ! -s "..." ]; then echo "Skipping empty file: $filename" ((skipped++)) ... # Skip to next iteration fi # Skip if file is older than 7 days if [ $(find "$logfile" -mtime +7 | wc -l) -gt 0 ]; then echo "Skipping old file: $filename" ((skipped++)) ... # Skip to next iteration fi # Process the file echo "Processing: $filename" # Add your processing logic here ((processed++)) done echo "Summary: Processed $processed files, Skipped ... files"
Copied!

Expected output:

Skipping empty file: error.log Skipping old file: system.log Processing: access.log Processing: auth.log Skipping empty file: debug.log Processing: messages.log Summary: Processed 3 files, Skipped 3 files

#!/bin/bash # selective_file_processor.sh # Complete solution for selective file processing log_dir="/var/log" processed=0 skipped=0 for logfile in "$log_dir"/*.log do filename=$(basename "$logfile") # Skip if file is empty if [ ! -s "$logfile" ]; then echo "Skipping empty file: $filename" ((skipped++)) continue # Skip to next iteration fi # Skip if file is older than 7 days if [ $(find "$logfile" -mtime +7 | wc -l) -gt 0 ]; then echo "Skipping old file: $filename" ((skipped++)) continue # Skip to next iteration fi # Process the file echo "Processing: $filename" # Add your processing logic here ((processed++)) done echo "Summary: Processed $processed files, Skipped $skipped files"

Nested Loops - Multi-Dimensional Processing

Network Connectivity Matrix

#!/bin/bash # network_matrix.sh servers=("web1:192.168.1.10" "db1:192.168.1.20") for source in "${servers[@]}" do source_name="${source%%:*}" for dest in "${servers[@]}" do dest_ip="${dest##*:}" if ping -c 1 -W 1 "$dest_ip" &>/dev/null; then echo "$source_name → $dest_ip: ✅" else echo "$source_name → $dest_ip: ❌" fi done done
Copied!
Learning Checkpoint
How many total ping tests will the network connectivity matrix perform with 2 servers?
2
Think about nested loops
Not quite. With nested loops, each source server tests connectivity to each destination server, creating more combinations.
3
Calculate all combinations
Incorrect. With 2 servers in both the outer and inner loops, the total is 2 × 2 combinations.
4
2 sources × 2 destinations = 4 tests
Correct! Each of the 2 source servers tests each of the 2 destination servers, resulting in 2 × 2 = 4 total ping tests (including servers pinging themselves).
8
Too many tests
That's not right. The calculation is 2 servers × 2 servers = 4 tests, not 8.

Lab Exercise 3: Security Compliance Checker

As a security engineer, you need to build a compliance checker that validates multiple configuration files against security requirements. This exercise demonstrates nested loops for comprehensive system validation.

#!/bin/bash # compliance_checker.sh # Check system configurations against security requirements # Define configuration files to check config_files=( "/etc/ssh/sshd_config" "/etc/passwd" ) # Define security requirements (setting:expected_value) ssh_requirements=( "PermitRootLogin:no" "PasswordAuthentication:no" "Protocol:2" ) passwd_requirements=( "root:x:0:0" # Check root account is properly configured ) echo "=== Security Compliance Check ===" compliance_status="PASS" # Loop through configuration files for file in "${config_files[@]}" do echo "" echo "Checking: $file" # Select appropriate requirements based on file if [[ "$file" == *"sshd_config" ]]; then requirements=("${ssh_requirements[@]}") elif [[ "$file" == *"passwd" ]]; then requirements=("${passwd_requirements[@]}") else continue fi # Check each requirement for req in "${requirements[@]}" do setting="${req%%:*}" expected="${req##*:}" # Check if setting exists with expected value if [[ "$file" == *"sshd_config" ]]; then if grep -q "^$setting $expected" "$file" 2>/dev/null; then echo " ✅ $setting: COMPLIANT" else echo " ❌ $setting: NOT COMPLIANT (expected: $expected)" compliance_status="..." fi elif [[ "$file" == *"passwd" ]]; then if grep -q "^$expected" "$file" 2>/dev/null; then echo " ✅ Root account: COMPLIANT" else echo " ❌ Root account: NOT COMPLIANT" compliance_status="..." fi fi done done echo "" echo "=== Overall Compliance Status: ... ==="
Copied!

Expected output:

=== Security Compliance Check === Checking: /etc/ssh/sshd_config ✅ PermitRootLogin: COMPLIANT ✅ PasswordAuthentication: COMPLIANT ❌ Protocol: NOT COMPLIANT (expected: 2) Checking: /etc/passwd ✅ Root account: COMPLIANT === Overall Compliance Status: FAIL ===

Learning Checkpoint
In the compliance checker, what does "${req%%:*}" extract from "PermitRootLogin:no"?
The entire string "PermitRootLogin:no"
%% performs extraction
Not correct. The %% operator removes a pattern from the end of the string, not returns the whole string.
Only "PermitRootLogin"
Removes :* from the end
Correct! The ${req%%:*} syntax removes the longest match of :* from the end, leaving only "PermitRootLogin" - the part before the colon.
Only "no"
That would be ##*:
Incorrect. To extract "no", you would use ${req##*:} which removes everything up to and including the colon.
The colon character ":"
Pattern matching removes the colon
That's not right. The pattern matching removes the colon along with everything after it, not extracts it.
