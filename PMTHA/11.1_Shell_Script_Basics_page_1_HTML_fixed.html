Shell Script Basics (Shebang, Execution) - Mastering the Linux Command Line

Welcome to the wonderful world of Linux shell scripting! Imagine being able to tell your computer to do hundreds of tasks while you sip your coffee - that's the power of shell scripts! Just as master chefs have their recipes, system administrators have their scripts. Today, you'll transform from a command-line typist to a script-writing wizard!

Fun Fact: The term "shebang" (#!) comes from the combination of "sharp" (#) and "bang" (!). Some say it sounds like a superhero move - and in a way, it is! It gives your scripts superpowers to run automatically.

11.1.1. What Are Shell Scripts? (Your Computer's To-Do List)

Understanding the Magic ✨

Think of shell scripts as giving your computer a detailed to-do list. Instead of being your personal assistant who needs constant instructions, your Linux system becomes a self-sufficient worker who knows exactly what to do!

Real-world analogy: Shell scripts are like those amazing morning routines - but for computers:

  • Wake up (boot system) ☕
  • Brush teeth (clean temp files) 🪥
  • Make breakfast (start services) 🍳
  • Check news (monitor logs) 📰

Let's See Some Scripts in Action!

Knowledge Check Box
If you had to do the same 10 tasks every morning on 100 servers, would you rather:
Type commands 1000 times
Manually enter each command on each server every time.
Your fingers would get quite a workout! This approach is time-consuming, error-prone, and not scalable. Automation is your friend!
Write one script and run it 100 times
Create a shell script once and execute it on all servers.
Correct! This is the power of shell scripting. Write once, run anywhere. Your fingers (and your time) will thank you for choosing this efficient approach!

11.1.2. The Mighty Shebang (#!) - Your Script's Identity Card

What's a Shebang? 🎭

The shebang is like your script's passport - it tells Linux exactly which interpreter to use. Without it, Linux is like a confused tourist trying to speak the wrong language!

#!/bin/bash → "Hey Linux, speak Bash please!" #!/bin/python3 → "Linux, let's talk Python!" #!/bin/sh → "Just use basic shell talk!"
Copied!

Creating Your First Shebang Script

Let's create a friendly greeter script:

# Step 1: Start with the shebang echo '#!/bin/bash' > hello_world.sh
Copied!
Think About It
What would happen if you ran a shell script without the shebang line?
Script runs perfectly
The script would execute without any issues.
Not quite. Without a shebang, the system might use the wrong interpreter or fail to execute the script properly.
Linux uses default shell
Linux would use the current shell to interpret the script, which might not be what you intended.
Correct! Without a shebang, Linux uses the current shell to run the script. This could cause issues if your script uses features specific to a particular shell like bash.
Script deletes itself
The script would self-destruct for security reasons.
That would be dramatic! Linux doesn't delete scripts just because they lack a shebang. It simply might not execute them as expected.
# Step 2: Add some personality echo 'echo "Hello from Linux Land!"' >> hello_world.sh echo 'echo "The time is: $(date +%T)"' >> hello_world.sh # Step 3: Admire your creation cat hello_world.sh
Copied!
Mini-Lab: Shebang Detective
Your Mission: Create three scripts with different shebangs and see the differences!
# Script 1: The Bash script echo '#!/bin/bash' > bash_test.sh echo 'echo "Bash version: $BASH_VERSION"' >> bash_test.sh # Script 2: The portable script echo '#!/bin/sh' > portable_test.sh echo 'echo "I work everywhere!"' >> portable_test.sh # Script 3: The flexible script echo '#!/usr/bin/env bash' > flexible_test.sh echo 'echo "I find bash wherever it lives!"' >> flexible_test.sh
Copied!
Which shebang would you use for maximum portability across different Linux systems?
#!/bin/bash
Use the bash interpreter at a fixed location.
This assumes bash is always at /bin/bash, which isn't true on all systems. Some systems might have bash in /usr/bin/bash or elsewhere.
#!/bin/sh
Use the basic POSIX shell.
While portable, this limits you to basic shell features. You can't use bash-specific features like arrays or [[ ]] conditionals.
#!/usr/bin/env bash
Use env to find bash wherever it's installed.
Correct! The env command searches the PATH for bash, making your script work regardless of where bash is installed. It's like having a GPS for finding bash!

Pro Tip: The #!/usr/bin/env bash shebang is like having a GPS for finding bash - super useful when bash plays hide-and-seek in different locations!

11.1.3. Making Scripts Executable (Giving Scripts Their Running Shoes) 👟

Understanding Permissions - The VIP List 📋

Linux permissions are like a nightclub bouncer - they decide who gets in (read), who can change things (write), and who can party (execute)!

Before chmod: -rw-r--r-- → "You can look, but don't touch (or run)!" After chmod: -rwxr-xr-x → "You can look, touch, AND run!"
Copied!

Let's Give Our Script Permission to Run!

# Check current permissions ls -l hello_world.sh
Copied!

Output might look like: -rw-r--r-- 1 user user 75 Nov 21 10:30 hello_world.sh

# Give yourself execute permission chmod u+x hello_world.sh # Check again - spot the difference! ls -l hello_world.sh
Copied!

Now you'll see: -rwxr--r-- (Notice the 'x' in position 4? That's your execute permission!)

🎮 Interactive Exercise: Permission Playground

# Create a test script echo '#!/bin/bash' > permission_test.sh echo 'echo "🎉 I can run!"' >> permission_test.sh # Try to run it (this will fail) ./permission_test.sh # Error: Permission denied # Now fix it! chmod u+x permission_test.sh # Try again (success!) ./permission_test.sh
Copied!
Reflection Question
Why does Linux require you to explicitly grant execute permission to scripts?
To make life difficult
Linux enjoys creating extra steps for users.
Linux isn't trying to be mean! There's actually a very good reason for this requirement.
Security protection
It prevents accidental or malicious execution of files.
Correct! Security is like a good lock - better safe than sorry! This prevents downloaded files or email attachments from automatically running and potentially harming your system. You must consciously decide to make a file executable.
Historical tradition
It's just how things have always been done.
While Unix/Linux has many traditions, this one exists for a practical security reason, not just because "that's how it's always been."
Performance optimization
Non-executable files run faster when needed.
The execute permission doesn't affect performance. It's purely a security measure to control what can be run on your system.

💭 Remember: In the world of Linux, with great power comes great permissions! The execute bit is your script's license to run.
