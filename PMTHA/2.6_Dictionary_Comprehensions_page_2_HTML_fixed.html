🏗️ Nested Dictionary Comprehensions: Managing Complex Medical Data

When Medical Data Gets Hierarchical

Real medical data is rarely flat - it's like a Russian nesting doll! 🪆 Patients have multiple visits, each visit has multiple tests, each test has multiple parameters. Nested comprehensions help us navigate this complexity.

🏥 Example: Multi-Site Clinical Trial Data

# Clinical trial: New diabetes medication efficacy # =============================================== # Structure: Site → Patient → Week → HbA1c reading # ================================================ trial_data = { "Boston_General": { "BG001": {"week_0": 8.2, "week_4": 7.5, "week_8": 7.1}, "BG002": {"week_0": 9.1, "week_4": 8.3, "week_8": 7.8}, }, "Chicago_Med": { "CM001": {"week_0": 7.9, "week_4": 7.2, "week_8": 6.8}, "CM002": {"week_0": 8.5, "week_4": 7.9, "week_8": 7.3}, } } # Calculate improvement for each patient # ====================================== patient_improvements = { site: { patient: { "initial": readings["week_0"], "final": readings["week_8"], "improvement": readings["week_0"] - readings["week_8"], "percent_change": ((readings["week_0"] - readings["week_8"]) / readings["week_0"]) * 100 } for patient, readings in patients.items() } for site, patients in trial_data.items() } # Display results with visual indicators # ====================================== print("📊 Clinical Trial Results - HbA1c Improvement") print("=" * 50) for site, patients in patient_improvements.items(): print(f"\n🏥 {site}:") for patient, data in patients.items(): emoji = "🎉" if data["improvement"] > 1.0 else "✅" print(f" {patient}: {data['initial']}% → {data['final']}% " f"({emoji} -{data['improvement']:.1f}%, " f"{data['percent_change']:.1f}% improvement)")
Copied!
Knowledge Check: Nested Dictionary Comprehension Structure
In the clinical trial data example above, what is the correct structure of the nested dictionary comprehension for patient_improvements?
A) {site: {patient: calculations} for site in trial_data for patient in patients}
Using sequential for loops without proper nesting
Not quite. This syntax doesn't properly access the nested structure. The variable 'patients' is not defined in this scope.
B) {site: {patient: calculations for patient, readings in patients.items()} for site, patients in trial_data.items()}
Nested comprehension with proper item unpacking
Correct! This properly nests two dictionary comprehensions, unpacking both the outer dictionary (sites) and inner dictionaries (patients) with .items().
C) {patient: {site: calculations} for patient in patients for site in trial_data}
Inverted structure with patient as outer key
This reverses the data structure, making patient IDs the outer keys instead of sites. Also, 'patients' is undefined in this scope.
D) {site: [patient: calculations for patient in patients] for site in trial_data}
Mixed list and dictionary syntax
This syntax is invalid. You cannot have key:value pairs inside a list comprehension using square brackets.

🧬 Advanced: Genomic Variant Analysis

# Patient genomic variants by gene and type # ========================================= genomic_data = { "PATIENT_001": { "BRCA1": {"missense": 2, "nonsense": 0, "frameshift": 1}, "TP53": {"missense": 1, "nonsense": 1, "frameshift": 0} }, "PATIENT_002": { "BRCA1": {"missense": 0, "nonsense": 0, "frameshift": 0}, "TP53": {"missense": 3, "nonsense": 0, "frameshift": 1} } } # Calculate total variants per patient per gene # ============================================= variant_summary = { patient: { gene: sum(variants.values()) for gene, variants in genes.items() } for patient, genes in genomic_data.items() } # Identify high-risk patients (>2 variants in any gene) # ================================================== high_risk = { patient: genes for patient, genes in variant_summary.items() if any(count > 2 for count in genes.values()) }
Copied!
Knowledge Check: High-Risk Patient Identification
Based on the genomic variant analysis code above, which statement correctly describes the high_risk dictionary comprehension?
A) It includes patients who have more than 2 variants total across all genes
Checking total variant count across all genes
Not correct. The code uses any() to check if ANY individual gene has more than 2 variants, not the total across all genes.
B) It includes patients who have more than 2 variants in at least one gene
Checking if any single gene exceeds the threshold
Correct! The any() function returns True if at least one gene has a count > 2, which is exactly what this comprehension checks for.
C) It includes patients who have exactly 2 variants in any gene
Checking for exactly 2 variants
The condition checks for counts > 2 (greater than 2), not equal to 2.
D) It includes all patients and flags which genes have more than 2 variants
Including all patients with gene-level flags
The comprehension filters patients using an if clause, so it only includes patients meeting the criteria, not all patients.

According to the risk scoring rules, what would be the total risk score for EMP002 with the following values?
- BMI: 31.2
- BP Systolic: 142
- Cholesterol: 240
- Glucose: 115
- HbA1c: 6.8
A) 6 points
Underestimating some risk factors
Not quite. Let's recalculate: BMI 31.2 (>30) = 2 points, BP 142 (>140) = 2 points, Cholesterol 240 = 2 points, Glucose 115 (>100) = 1 point, HbA1c 6.8 (>6.5) = 2 points.
B) 7 points
Missing one risk factor
Close, but check the cholesterol scoring. At exactly 240, it meets the >200 threshold (1 point) and the ≥240 threshold (another point), totaling 2 points for cholesterol.
C) 8 points
Correctly applying all risk scoring rules
Correct! BMI >30: 2 points, BP >140: 2 points, Cholesterol ≥240: 2 points, Glucose >100: 1 point, HbA1c >6.5: 2 points = 8 total points.
D) 9 points

Too high. Remember that each metric has a maximum of 2 points, and glucose 115 only meets the >100 threshold (1 point), not the >126 threshold.

🎯 Pro Tips and Best Practices

1. Keep It Readable!

# ❌ Too complex - hard to debug # ============================= result = {k:{k2:v2*2 for k2,v2 in v.items() if v2>5} for k,v in data.items() if sum(v.values())>20} # ✅ Better - clear and maintainable # ================================= filtered_data = { patient_id: { test: value * 2 for test, value in test_results.items() if value > 5 } for patient_id, test_results in data.items() if sum(test_results.values()) > 20 }
Copied!
Knowledge Check: Code Readability
What makes the second version of the code more readable than the first?
A) It uses shorter variable names
Making code more concise
Actually, the opposite is true! The second version uses longer, more descriptive variable names like 'patient_id' instead of 'k'.
B) It uses descriptive variable names and proper formatting
Clear naming and multi-line formatting
Correct! Descriptive names like 'patient_id' and 'test_results', plus multi-line formatting with proper indentation, make the code much easier to understand and maintain.
C) It runs faster
Performance optimization
Readability improvements typically don't affect performance. Both versions would execute at the same speed.
D) It uses fewer lines of code
Code compactness
The second version actually uses more lines to improve readability. Sometimes more lines make code easier to understand!

2. Use Helper Functions for Complex Logic

def calculate_risk_score(vitals): """Calculate cardiovascular risk score""" score = 0 if vitals['bp'] > 140: score += 2 if vitals['cholesterol'] > 240: score += 2 if vitals['age'] > 65: score += 1 return score # Clean comprehension using helper function # ========================================= risk_assessment = { patient_id: calculate_risk_score(vitals) for patient_id, vitals in patient_data.items() }

Knowledge Check: Helper Function Benefits
Why is using a helper function like calculate_risk_score() beneficial in dictionary comprehensions?
A) It makes the code run faster
Performance improvement
Helper functions don't necessarily improve performance. The main benefit is code organization and readability.
B) It separates complex logic from the comprehension, improving readability and reusability
Clean separation of concerns
Excellent! Helper functions keep comprehensions clean and simple, make complex logic reusable, and are easier to test and debug separately.
C) It is required by Python syntax
Syntax requirement
Helper functions are optional. You can put all logic directly in the comprehension, but it may become hard to read.
D) It reduces memory usage
Memory optimization
Helper functions don't reduce memory usage. The same operations occur whether in the function or inline.

Knowledge Check: Generator vs Dictionary Comprehension
What is the main difference between a generator expression (using parentheses) and a dictionary comprehension (using curly braces) for large datasets?
A) Generator expressions are always faster
Speed advantage
Not necessarily. Generators can be slower for small datasets due to overhead, but they excel with large datasets.
B) Dictionary comprehensions can only process dictionaries
Input type restriction
Dictionary comprehensions can process any iterable and create dictionaries from them, not just existing dictionaries.
C) Generator expressions process items one at a time, using less memory
Lazy evaluation and memory efficiency
Correct! Generators use lazy evaluation, processing items on-demand rather than creating all results at once in memory. This is crucial for large genomic datasets.
D) There is no difference; they are interchangeable
Identical functionality
They have very different behaviors. Generators produce items on-demand, while comprehensions create complete data structures immediately.
