📊 Understanding map() - Transform All Data

🧪 Mini-Exercise: Using map() with Lambda
Complete the following code to see how map() transforms data:
# Step 1: Simple example - Square all numbers numbers = [1, 2, 3, 4, 5] squared = list(map(lambda x: x**2, numbers)) print(f"Squared: {squared}") # Step 2: Medical application - Temperature conversion temperatures_c = [36.5, 37.2, 38.1, 37.8, 36.9] temperatures_f = list(map(lambda c: (c * 9/5) + 32, temperatures_c)) # Pretty print with labels for c, f in zip(temperatures_c, temperatures_f): print(f"{c}°C = {f:.1f}°F")

🔍 Understanding filter() - Select Specific Data

Learning Checkpoint
Given the code:
temperatures_c = [36.5, 37.2, 38.1, 37.8, 36.9]
fever_patients = list(filter(lambda temp: temp >= 38, temperatures_c))
How many patients have a fever (≥38°C)?
0 patients
No patients have a temperature of 38°C or higher.
Not correct. Look at the temperatures again - one value is 38.1°C, which is above the fever threshold.
1 patient
One patient has a temperature of 38°C or higher.
Correct! Only one patient (38.1°C) has a fever. The filter() function with lambda efficiently identifies patients meeting specific clinical criteria.
2 patients
Two patients have temperatures of 38°C or higher.
Incorrect. Only 38.1°C meets the criterion. The value 37.8°C is close but still below the 38°C threshold.
3 patients
Three patients have temperatures of 38°C or higher.
That's not right. Remember, the filter condition is temp >= 38. Only 38.1°C satisfies this condition.

📈 Understanding sorted() - Order Your Data

The sorted() function becomes incredibly powerful when combined with lambda functions to sort complex medical data:

# Patient glucose data (name, glucose_mg/dL) patient_glucose = [ ("Alice", 95), # Normal ("Bob", 125), # Pre-diabetic ("Carol", 108), # Normal ("David", 87), # Normal ("Eve", 145) # Pre-diabetic ] # Sort by glucose level (ascending) sorted_by_glucose = sorted(patient_glucose, key=lambda x: x[1]) print("Patients by glucose level:") for name, glucose in sorted_by_glucose: status = "Normal" if glucose < 100 else "Pre-diabetic" if glucose < 126 else "Diabetic" print(f" {name}: {glucose} mg/dL ({status})")
Copied!
Medical Term Clarification
According to medical guidelines, which glucose level indicates pre-diabetes?
< 100 mg/dL
Glucose levels below 100 mg/dL indicate pre-diabetes.
Incorrect. Glucose levels below 100 mg/dL are actually normal, not pre-diabetic.
100-125 mg/dL
Glucose levels between 100 and 125 mg/dL indicate pre-diabetes.
Correct! Pre-diabetes is diagnosed when fasting glucose is between 100-125 mg/dL. This range indicates impaired glucose metabolism but not yet full diabetes.
≥ 126 mg/dL
Glucose levels of 126 mg/dL or higher indicate pre-diabetes.
Not quite. Glucose levels ≥ 126 mg/dL actually indicate diabetes, not pre-diabetes.
80-99 mg/dL
Glucose levels between 80 and 99 mg/dL indicate pre-diabetes.
Incorrect. This range is actually within the normal glucose levels, not pre-diabetic.

Real-World Connection: Clinical research teams use these exact patterns to identify patients meeting study criteria, sort by disease severity, or transform laboratory values for analysis. This approach is fundamental in precision medicine for stratifying patients based on molecular profiles.

Lab Exercise 3: Genetic Variant Filtering

🎓 Learning Objective

Use lambda functions with filter() to identify pathogenic genetic variants from a list of variant data.

Medical Context: In genetics, variants with very low frequency in the population (< 1%) are often associated with rare diseases. These are prime candidates for further investigation!

📝 Scaffolded Exercise

Pattern Recognition Challenge
Looking at this genetic variant data:
[("BRCA1_v1", 0.0001), ("APOE_v2", 0.15), ("TP53_v3", 0.0005)]
To filter variants with frequency < 0.01, which lambda function would you use?
lambda variant: variant < 0.01
Compare the entire variant tuple to 0.01
Incorrect. This compares the entire tuple to 0.01, which doesn't make sense. You need to access the frequency value within the tuple.
lambda variant: variant[0] < 0.01
Check if the gene name is less than 0.01
Not right. variant[0] is the gene name (a string), not the frequency. You can't compare a string to a number.
lambda variant: variant[1] < 0.01
Check if the frequency (second element) is less than 0.01
Correct! variant[1] accesses the frequency value (the second element of the tuple), which is what we need to compare against 0.01.
lambda x, y: y < 0.01
Unpack the tuple into x and y, then check y
Incorrect syntax. Lambda functions used with filter() receive one argument (the whole tuple), not multiple unpacked values.

🎯 Complete Solution

Now let's see the complete solution for filtering genetic variants:

# Complete solution genetic_variants = [ ("BRCA1_v1", 0.0001), # BRCA1: Breast cancer gene ("APOE_v2", 0.15), # APOE: Alzheimer's risk gene ("TP53_v3", 0.0005), # TP53: Tumor suppressor gene ("LDLR_v4", 0.08), # LDLR: Cholesterol gene ("CFTR_v5", 0.0002) # CFTR: Cystic fibrosis gene ] # Filter rare variants rare_variants = list(filter(lambda variant: variant[1] < 0.01, genetic_variants)) print(f"Rare variants: {rare_variants}") # Bonus: Extract just the variant names rare_variant_names = list(map(lambda v: v[0], rare_variants)) print(f"Rare variant names: {rare_variant_names}") # Extra bonus: Create a summary report print("\n📊 Variant Analysis Report:") print(f"Total variants analyzed: {len(genetic_variants)}") print(f"Rare variants found: {len(rare_variants)}") print(f"Percentage rare: {len(rare_variants)/len(genetic_variants)*100:.0f}%") # Super bonus: Find ultra-rare variants (< 0.0001) ultra_rare = list(filter(lambda v: v[1] < 0.0001, genetic_variants)) print(f"Ultra-rare variants: {[v[0] for v in ultra_rare]}")
Copied!

Expected output:

Rare variants: [('BRCA1_v1', 0.0001), ('TP53_v3', 0.0005), ('CFTR_v5', 0.0002)] Rare variant names: ['BRCA1_v1', 'TP53_v3', 'CFTR_v5'] 📊 Variant Analysis Report: Total variants analyzed: 5 Rare variants found: 3 Percentage rare: 60% Ultra-rare variants: ['BRCA1_v1']

Common Pitfalls and Debugging

⚠️ Watch Out For These Common Mistakes:

Syntax Check
Which lambda function has correct syntax?
lambda x x**2
Lambda without colon
SyntaxError! Lambda functions require a colon (:) between the parameters and the expression.
lambda x: x**2
Lambda with proper colon syntax
Correct! This lambda has the proper syntax: parameter(s), colon, then expression.
lambda: x: x**2
Lambda with extra colon
SyntaxError! You can't have two colons. The correct format is: lambda parameters: expression
lambda (x): x**2
Lambda with parentheses around parameter
In Python 3, you don't need (and shouldn't use) parentheses around single lambda parameters.
Lambda Limitations
Why can't you use print() inside a lambda function?
print() is too slow
Lambda functions need to be fast, and print() is slow
Performance isn't the issue. The real reason is about the difference between statements and expressions.
Lambdas can only contain expressions
print() is a statement, not an expression that returns a value
Correct! Lambda functions can only contain expressions (things that evaluate to a value), not statements like print(), if blocks, or loops.
print() requires import
You need to import print before using it in lambda
print() is a built-in function and doesn't require import. The issue is that lambdas can't contain statements.
Lambda functions are read-only
Lambda functions can't produce output
Lambda functions can return values, they just can't contain statements like print().
Best Practices
When should you use a regular function instead of a lambda?
When processing medical data
Medical data always requires regular functions
The type of data doesn't determine whether to use lambda. It's about the complexity of the logic.
When using map() or filter()
These functions require regular functions, not lambdas
Actually, map() and filter() work perfectly with lambda functions for simple operations.
When the logic is complex or multi-line
Complex logic with multiple conditions or steps
Correct! If your logic requires multiple lines, complex conditions, or would be hard to read as a single expression, use a regular function instead.
Never - always use lambdas
Lambda functions are always more efficient
Lambda functions aren't always better. Use them for simple, one-line operations. For complex logic, regular functions are more readable.

💡 Debugging Tip: If your lambda is longer than one line when written out, it's probably too complex!
